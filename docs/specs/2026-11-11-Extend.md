# Claude OS manages itself through the `claude-os` MCP — spec

Status: draft · Owner: the user · Date: 2026-11-11

## Intent
Sessions should be able to run Claude OS itself: tabs, the server, widgets, numbers, the planner, the board, settings, actions, projects, memory, admin and documents. Today each of these has an HTTP route and a helper, but most have no MCP tool, so a session has to ask the user to click. Every new tool is a thin wrapper over the helper that already exists. Each one follows the rootMcp pattern (helper → `ctx.audit` → `ctx.invalidate` → `ok`/`fail`) and is allowed without a prompt in root and work tabs. The user's policy: changing Claude OS is Claude's business, any change is fine. The two lines that stay are command approval and the `data/` write deny.

## Goals
1. Root and work tabs get every tool below, allowed without a prompt. `mcpTools.test.ts` stays green with `PROMPTED_TOOLS.work` and `.root` unchanged.
2. **P1 Tabs:** `list_tabs`, `close_tab(id?, force?)`, `rename_tab`, `set_tab_options`, `interrupt_tab`, `reset_tab`, `send_to_tab`, `clear_tab_progress`. `open_session`, `open_sessions` and `resume_session` move to work tabs too. `ui_action` gains `focus` (a tab) and `reload` (all windows).
3. **P2 Server:** `app_status`, `restart_claude_os` (every tab), `reload_config` and `rebuild_web`. `rebuild_web` runs the vite build, then broadcasts a reload.
4. **P3 Widgets:** `list_widgets` (definitions and current values), `add_widget`, `update_widget`, `remove_widget`, `place_widget` and `set_widget_value(id, value)`. The last one works on a new `push` widget type, and its value survives a restart.
5. **P4 Numbers:** `get_analytics`, `get_overview`, `get_usage_log`, `get_forecast` and `get_audit`, plus `set_tab_progress` for another tab.
6. **P5 Planner:** `list_planner_notes`, `read_planner_note` (with version), `add_planner_note(text, folder?)`, `add_planner_item(note, text)` and `set_planner_note_text` (work and root). Also `rename_planner_note`, `move_planner_note_folder`, `remove_planner_note` and `planner_folder(op: add|rename|color|order|remove)`. The "only the user creates folders" rule goes.
7. **P6 Kanban:** `remove_kanban_card`, `set_kanban_prefix` and `list_card_sessions`. `add_kanban_card` moves to work tabs.
8. **P7 Settings:** `get_settings`, `set_project_settings`, `set_home_layout` and `set_universe`. Each write is audited.
9. **P8 Actions:** `list_actions`, `add_action`, `update_action`, `remove_action` and `run_action`. `run_action` runs only approved actions; an unapproved one fails and names what the user must approve.
10. **P9 Projects:** `list_projects` (work tabs too), `connect_project` and `set_project_icon`.
11. **P10 Memory:** `read_memory_note` and `write_memory_note(id, markdown, version)`.
12. **P11 Admin:** `list_skills`, `list_mcp_servers`, `list_plugins`, `add_skill`, `remove_skill`, `add_mcp_server`, `remove_mcp_server`, `read_claude_md` and `save_claude_md` (with version).
13. **P12 Documents:** `remove_document` and `remove_document_knowledge`.
14. **Restart safety.** A restart from any tab continues every busy tab, the caller included. A test proves it from a work tab.
15. **Closing.** `close_tab` refuses a busy foreign tab without `force: true`. Closing the caller's own tab is deferred, so the answer leaves first. The root tab stays unclosable.

## Non-goals
- Approving commands of actions, widgets or widget views. Approval stays in the interface, and `data/` stays out of a session's reach.
- Plugin enable and disable. These keep their preview-and-confirm card in `OsPlugins.tsx`.
- Service and setup sessions get nothing new. Continuing service jobs after a restart is out of scope.
- New REST routes or interface screens. Web changes are limited to the two `ui_action` cases and the `push` widget type.
- Editing a project's files: that stays with the normal tools and permission mode.

## Anti-goals
- A restart that loses a turn, a queued message or the caller's own work.
- A tool that approves a command or writes `data/approved-commands.json`.
- A closed tab whose tool call never answered, so the model waits forever.
- An always-loaded prompt that grows. Only deferred tool names may be added.
- `rootMcp.ts` or `manager.ts` over their caps, or a raised override.
- Logic copied from a route into a tool instead of moved into a shared helper. The two would drift apart.

## Design

### Access to the helpers
Add `ctx.os?: OsApi` in `server/context.ts`, set in `registerTools` next to `ctx.settings` and `ctx.kit`. It holds the factory instances the tools need: `widgets`, `actions`, `settings` (`view`, `setProject`, `setUniverse`, `setHome`), `skills`, `mcp`, `claudeMd`, `osPlugins` (`list` only), `projectIcons` and `forecast`. The analytics, overview and usage tools call the exported query functions with `ctx.db`. Planner, kanban and documents use their exported functions. Route-inline logic moves into helpers that both the route and the tool call: projects `connect` (`manage.ts:300`), the planner folder handlers (`planner.ts:429-444`) and `/api/audit` (`journal/index.ts:324`).

### Files
Each group goes in its own file beside `kanbanTools.ts`: `server/chat/tabTools.ts`, `appTools.ts`, `widgetTools.ts`, `numberTools.ts`, `plannerTools.ts`, `settingsTools.ts`, `actionTools.ts`, `adminTools.ts`. Projects and memory go into `dispatchTools.ts` and `memoryTool.ts` if they fit; otherwise into `projectTools.ts`. The kanban and document additions go into `kanbanTools.ts` and the document tools; `documentTools` moves out of `rootMcp.ts` if `rootMcp.ts` needs the room.

`server/chat/osTools.ts` exports two things:
- `osTools(ctx, chat, tabId, project)`: the array spread into both `createRootMcp` and `createPlannerMcp`.
- `OS_TOOLS`: the `mcp__claude-os__*` names, built from the same list and spread into both `allowedTools` in `manager.ts:320-321`.

`rootMcp.ts` and `manager.ts` each change by about one line per spread. Existing root tools that move to work tabs are `list_projects`, `open_session`, `open_sessions`, `resume_session`, `restart_claude_os`, `add_kanban_card` and `set_planner_note_text`. They move into `osTools` once, instead of being registered twice.

### P1 Tabs (`tabTools.ts`)
- `list_tabs`: `chat.list()`, mapped to `id, kind, title, project, cwd, status, attention, queued, progress, permissionMode`, with the caller marked `self: true`.
- `close_tab(id?, force?)`: `id` defaults to the caller.
  - Root: `fail` with the `rootTabClose` message.
  - Another tab with `status !== 'idle'` and no `force`: `fail('Tab is working; pass force: true to close it')`.
  - The caller: `setTimeout(() => chat.close(id), 400)` and `ok({ closing: true })`, the same delay as `ctx.restart`.
  - Otherwise: `chat.close(id)`.
  - Audit `tab.close`. `close()` already invalidates.
- `rename_tab(id, title)` and `set_tab_options(id, {model?, effort?, permissionMode?, order?})`: `chat.update(id, body)` (audit `tab.update`). `permissionMode` takes default, acceptEdits, auto or plan, the same enum as `open_session` (`PERMISSION_MODE`, `rootMcp.ts:221`). `bypassPermissions` is not offered; `session.ts:438` guards it anyway.
- `interrupt_tab(id)`, `reset_tab(id)` and `send_to_tab(id, text)` call the `chat.get(id)` methods the routes use. The answer of `send_to_tab` says whether the message was queued. All three refuse `id === tabId`: interrupting or resetting yourself cuts off this very answer, and messaging yourself loops. Audits: `tab.interrupt`, `tab.reset`, `tab.send`.
- `clear_tab_progress(id)` and `set_tab_progress(id, report)` (P4): `chat.reportProgress` and the route's `setProgress(null)`.
- `ui_action`:
  - `focus`: new `UiCommand` `{ action: 'focus'; tab: string }`. `uiCommand` checks the tab exists; `runUiCommand` switches to it.
  - `reload`: `{ action: 'reload' }`, `location.reload()` in each window, popouts included. `ws.ts:51` skips popouts for the other commands, so this case goes before that skip.

### P2 Server (`appTools.ts`)
- `app_status`: the `appStatus()` of `server/index.ts:86`, exposed as `ctx.appStatus?()`. Same shape as the route.
- `restart_claude_os`: the existing tool body (`planContinue`, audit, `ctx.restart`), moved to `appTools.ts` and given to every root and work tab. The audit text names the calling tab.
- `reload_config`: `widgets.reload()` and `ctx.invalidate('actions', 'widgets', 'settings')`, the same as the watcher (`tools/index.ts:247`). Audit `app.reload-config`.
- `rebuild_web`: `execFile(process.execPath, [vite bin, 'build', '--config', 'web/vite.config.ts'], { cwd: ctx.paths.repo })`. One build at a time; a second call while one runs returns the same promise. On success it broadcasts `{t:'ui', tabId, command:{action:'reload'}}` and answers with the duration. On failure it answers `fail` with the last lines of stderr and does not reload. Audit `app.rebuild-web`.

### P3 Widgets (`widgetTools.ts`)
- `list_widgets`: `widgets.list()`.
- `add_widget`, `update_widget`, `remove_widget` and `place_widget` go through the closure helpers. The new `update(id, patch)` sits beside `add` and uses `writeConfig`. A changed `command` or view is unapproved again by sha, as before. `widgets.ts` has room under its cap; check it.
- **The `push` type.**
  - Definition: `{ id, title, type: 'push' }`, added to the raw union (`widgets.ts:25-28`), to `WidgetDef` (`contract.ts:329`), to `root/reference/widgets.md` (touchpoint `widget-types`) and to the render path in `web/src/home/Widgets.tsx`, shown like a command value.

  - Removing the widget drops its value.
  - The file is in `data/` because the server, not a session, writes it.

### Flows
- **Happy path.** In a work tab, the user says "add a widget with the build status and keep it updated". Claude calls `add_widget({type:'push'})`, then `set_widget_value` on each step. The value shows on Home and survives `restart_claude_os`.
- **Failure: restart mid-build.** A work tab calls `restart_claude_os` while another tab runs a turn. Both are in `planContinue`, both get `CONTINUE_TEXT` after boot, and the other tab's queued messages wait in recovery (held).
- **Failure: busy foreign tab.** `close_tab(otherBusy)` without `force` answers `fail` and the tab stays.
- **Failure: own tab.** `close_tab()` answers `ok({closing:true})`, and the tab closes 400 ms later.
- **Failure: build.** `rebuild_web` fails, the answer holds the stderr tail, nothing reloads, and `dist/web` stays whatever vite left.
- **Failure: unapproved action.** `run_action` on an unapproved action answers `fail` and names the approval. Nothing runs.
- **Failure: stale versions.** `write_memory_note`, `set_planner_note_text`, `add_planner_item` or `save_claude_md` with a stale version answers `fail` with the 409 message. The tool re-reads and retries.

### Edge cases
- **Empty.** `list_*` on a missing `config/*.json` answers `[]` (readers tolerate missing files).
- **Concurrency.** Two `rebuild_web` calls share one build. Two widget or action writes race at the file level, last write wins, as with the UI today. `close_tab` on a tab that is already gone answers 404 → `fail`.
- **Permissions.** No new tool is in `PROMPTED_TOOLS`. `data/` stays denied for Edit. `set_tab_options` cannot reach `bypassPermissions`.
- **Restart on broken code.** A restart while another tab's server edit is half-written can boot broken code. Today a stale or failing boot is recovered by `desktop/serve.mjs` when the window opens; this spec adds no pre-check `[?]`.
- **i18n.** Tool descriptions are English. A description that names an interface element uses `PROMPT_LABELS` (`server/chat/profile.ts`). The only new web strings would be in the `push` widget; it reuses the command widget's.
- **The caller continued after its own restart** gets `CONTINUE_TEXT`, which says the restart happened, so it does not restart again.

### Touchpoints
- **`UiCommand` / `UI_ACTION_SET`** (typed): `contract.ts`, `uiCommand` in `rootMcp.ts`, `runUiCommand` in `web/src/lib/uiCommands.ts`. `ws.ts` routes `reload` before the popout skip.
- **Widget types** (check `widget-types`): `widgets.ts` raw union, `WidgetDef` in `contract.ts`, `root/reference/widgets.md`, `Widgets.tsx`.
- **MCP tools and `allowedTools`** (test): `osTools.ts` `OS_TOOLS`, both spreads in `manager.ts`, `mcpTools.test.ts`. `PROMPTED_TOOLS` is unchanged. `prompts name only existing tools` covers the edited `root/` docs.
- **`ServerMessage`**: unchanged; `reload` and `focus` ride `{t:'ui'}`.
- **`Topic`**: unchanged. Only existing topics are used: `tabs`, `widgets`, `settings`, `actions`, `planner`, `kanban`, `projects`, `documents`, `memory`, `skills`, `mcp`.
- **Route list in `contract.ts`**: unchanged; there are no new routes.
- **`PROMPT_LABELS`**: only if a description names an interface element.

### Rejected alternatives
- **Calling the routes through `ctx.app.inject`.** It needs no plumbing, but it goes through auth (`security.ts`), loses the types and turns errors into HTTP payloads.
- **One tool per group with an `op`.** It costs about 0.5 KB instead of about 1.8 KB, but descriptions get longer and ToolSearch matches worse. The user chose one tool per verb; only the five folder ops are grouped.
- **Separate `focus_tab` and `reload_window` tools.** The touchpoints recipe says interface commands go through `ui_action`, not separate tools.
- **A SQLite table for push values.** That is a schema change, and migrations need explicit permission. A JSON file in `data/` is enough for a few values.
- **Extending `planContinue`.** It already covers the caller and work tabs (Evidence).
