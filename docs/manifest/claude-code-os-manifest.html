1. The gist on one page

12 principles

  1. Determinism where mistakes are not allowed. Everything that must happen every time (formatting, types, tests, a ban on touching migrations) lives in hooks, deny rules, linters and CI — not in the prompt. CLAUDE.md is a set of wishes the model usually follows; a hook is the law. fact Anthropic says it plainly: if you add “IMPORTANT” to a line in CLAUDE.md and it still gets ignored, that is a signal the line belongs in a hook.
  2. Context is an expensive resource, even with a 1M-token window. The goal is the smallest set of high-signal tokens. CLAUDE.md ≤ 60 lines (the official ceiling is 200); the rest goes into path-scoped rules and skills that load on demand.
  3. Spec before code. We don’t work on an unclear task — first an interview (“ask questions until you can write a spec”), then SPEC.md, then a fresh session for the implementation.
  4. A check Claude can run by itself is the main multiplier. A test, a typecheck, a linter, a screenshot. Without a pass/fail signal, “done” means “looks done”.
  5. Small modules — for people and for models. File ≤ 300 lines, function ≤ 50, complexity ≤ 10. This is enforced (lint as error), not a wish.
  6. Compound: every mistake becomes a rule, every third repetition becomes a tool. After a fix — “write this into the rules so it doesn’t happen again”. If it happens twice, it moves from a rule into a hook/lint. If you did the same operation three times, it becomes a skill or an agent (section 11).
  7. Parallelism is the main accelerator. 3–5 worktree sessions + subagents + dynamic workflows (ultracode) for bulk tasks. One person is a “team lead”, not a “coder”.
  8. Memory in layers. Instructions (CLAUDE.md, rules) ≠ project knowledge (docs/solutions, ADR) ≠ Claude’s notes (auto memory) ≠ a personal wiki (Obsidian). Don’t mix them.
  9. The prompt cache is sacred. Model and effort are chosen at the start of a session; MCP servers and tools don’t change midway; /clear between unrelated tasks.
  10. A fresh reviewer. Review is done by a subagent/session that didn’t see the code being written (/code-review, a reviewer agent against the SPEC).
  11. One source of truth for style — the formatter/linter config and docs/rules/, which the rules reference. Not “wishes in your head”.
  12. Measure. /usage (breakdown by skills/subagents/MCP, cache hit rate), /insights, test time, number of fixes per feature.

Where the speedup comes from (an honest model)

Lever Mechanism Realistic multiplier
Parallelism 3–5 worktrees, background subagents, /batch, workflows ×2–4 in throughput
Less rework spec + plan + reviewer against the spec + the “touchpoints map” ×1.5–2 (every redo costs more than the first attempt)
Fast checks related tests in seconds, a Stop hook with typecheck, /verify ×1.3–2 per edit→check cycle
Context hygiene a short CLAUDE.md, /clear, subagents for noisy operations, LSP instead of reading files cost ÷2–3, quality ↑ (less “context rot”)
Autonomous loops /goal, Stop hooks, routines at night work continues while you sleep

Multiplied together, these give your “×5–×15” on good days; the sustainable expectation is ×3–6 in throughput with rising quality. The key condition is a deterministic check (principle 4): without it, parallelism just produces garbage faster.

The context of the era fact: in September 2026 Anthropic was merging more than 30,000 changes a day (about 2,500 in May) and rewrote its version control system (Scion), because “human-scale” infrastructure — source control, builds, CI — had become the bottleneck. Your project will hit the same wall: not the model, but tests, review and repository discipline.

3. The “Claude OS” architecture: seven layers

The system is not a single CLAUDE.md file but seven layers, each with its own job and its own “lifetime” in the context. The lower layers are deterministic (Claude Code itself executes them, not the model); the upper layers are probabilistic (the model reads them).

The key idea from the official best practices fact: every instruction comes in two forms — non-deterministic (a prompt, CLAUDE.md, a skill — the model decides whether to follow it) and deterministic (a hook, a deny rule, a managed setting — the harness always enforces it). The mapping:

What we control The model decides (layers L2–L3) Claude Code enforces (layers L0–L1)
What to do prompt, CLAUDE.md, skills hooks; skills with disable-model-invocation: true are launched only by you
What may be touched the auto mode classifier permissions.deny, sandbox in strict mode
When it is “done” asking for evidence, /goal, /code-review tests, typecheck, a Stop hook, CI
How much to spend effort, the model’s pace --max-turns, --max-budget-usd in -p, a spending limit
The final word Claude’s summary branch protection, a human on merge

The migration rule idea: every rule lives on a ladder chat → CLAUDE.md/rule → hook/lint → CI. If it repeats twice, move it one step down. After a month, CLAUDE.md holds only the things that genuinely require judgment.

Below is the skeleton your Claude should create in every project. The command names (pnpm …) are a TypeScript example; for Python, replace them with uv run … / pytest; the principles are the same.

Why exactly this way fact: the root CLAUDE.md and rules without paths load into every session and survive compaction (they are re-read from disk); rules with paths load only when working on matching files; skills put only their name and description into the context, the body loads on invocation; hooks take up no context at all. So “knowledge” is distributed by cost: always needed → CLAUDE.md, often needed → rules, sometimes needed → skills and docs.

4.1 CLAUDE.md — template (≤ 60 lines)

The only test for each line fact: “Can Claude find this by reading the code? Will it look?” If both are “yes”, delete the line. Don’t describe the architecture and folder structure — the model will read them itself. Do describe: verification commands, places where the code is deceptive, decisions that aren’t in the code, and everything you have corrected twice.

# <Project> — Claude Code instructions

## Commands (use these to check your own work)
- Install: pnpm install
- Typecheck: pnpm tsc --noEmit
- Lint (size limits are errors, do not raise them): pnpm lint
- Unit tests, fast: pnpm test:unit
- One test file: pnpm vitest run path/to/file.test.ts
- Related tests for changed files: pnpm vitest related --run <files>
- E2E (slow — run in a background subagent or CI): pnpm test:e2e
- Touchpoint check (shared concepts): pnpm check:touchpoints

## How we work (details in .claude/rules/00-workflow.md)
- Non-trivial task: read docs/specs/<feature>.md first. No spec → run /spec before coding.
- Shared concept changed (enum, event, notification, route, model, flag) → read docs/rules/touchpoints.md,
  update every consumer, run pnpm check:touchpoints.
- Finish = related tests + typecheck + lint green, evidence shown, lesson appended to docs/solutions/.

## Conventions (full standard: docs/rules/code-style.md)
- English only: identifiers, comments, commits, PR text.
- Use error helpers in src/lib/errors.ts; never throw raw strings.
- src/legacy/ is live but frozen: never copy its patterns into new code.

## Gotchas (things the code does not tell you)
- Integration tests need DATABASE_URL, see .env.example.
- src/gen/ is generated: never edit, run pnpm codegen.

## Decisions not visible in the code
- Tokens refresh server-side only (docs/adr/0003-token-refresh.md).
- Everything ships behind feature flags (docs/adr/0005-feature-flags.md).

Check: in a session, /context shows that the file is loaded; /doctor suggests cutting everything the model would find anyway; /doctor prompt-audit catches outdated and contradictory instructions (requires v2.1.283+). fact

4.2 .claude/rules — unconditional rules

.claude/rules/00-workflow.md (always loaded; this is the “rigor” you are missing):

# Workflow rules (always loaded)

## Task contract
Before the first edit on a non-trivial task, write one short message with:
1. Goal (one sentence) and the spec you follow (docs/specs/<slug>.md).
2. Done-check: the exact commands that will prove completion.
3. Scope: areas you will touch / will not touch.
4. Touchpoints: shared concepts affected (docs/rules/touchpoints.md).
Then proceed. Ask only when the contract cannot be filled from the spec.

## Systemic changes (the "it's a system, not a line" rule)
- A shared concept = enum member, event, notification type, API route, DB model/column,
  config key, feature flag, permission, i18n namespace.
- Before adding/changing one: `rg -n "<ExistingSibling>"` and list every place siblings appear
  (handlers, templates, tests, docs, types, migrations, i18n, admin UI, analytics).
  Mirror all of them for the new member. Missing ones are bugs, not "out of scope".
- Run `pnpm check:touchpoints` before finishing. Never disable or edit the check to pass.

## Finishing
- Show command output for: related tests, typecheck, lint, check:touchpoints.
- If the user corrected you: append a row to docs/rules/common-mistakes.md and say whether
  it should become a lint rule / hook / touchpoint check.
- Surgical changes only: no reformatting, renaming or "tidying" of unrelated code.
- Never commit secrets; never edit files under migrations/ or src/gen/ (hooks block it anyway).

.claude/rules/10-code-standard.md (short; the full text is docs/rules/code-style.md, section 6):

# Code standard (always loaded; full text: docs/rules/code-style.md)
- English only for identifiers, comments, docstrings, commit messages, PR text.
- Limits are lint errors: file ≤ 300 lines (UI components ≤ 400), function ≤ 50, class ≤ 200,
  cyclomatic complexity ≤ 10, nesting ≤ 4, parameters ≤ 4. Over the limit → /split-file first.
- One module = one responsibility; one exported class per file; file named after its export.
- Names: full words; booleans are predicates (isActive, hasAccess); functions are verbs; types are nouns.
- Comments say WHY, not WHAT. No commented-out code, no TODO without an issue id, no debug prints.
- No abstraction for single use, no speculative flexibility, simplest code that passes the tests.
- Dead code is deleted. knip (TS) / ruff F401 (Py) must stay clean.
- Formatting is the formatter's job (runs on every edit). Never add eslint-disable / noqa / @ts-ignore.

.claude/rules/20-mistakes.md — the top 10 mistakes of this particular project (Claude fills it from docs/rules/common-mistakes.md; ≤ 30 lines; example):

# Known mistakes (top list; full ledger: docs/rules/common-mistakes.md)
- New notification type without channel map entry, template, prefs label and admin filter.
- Hardcoded Russian UI strings instead of i18n keys.
- Appending to a 900-line file instead of extracting a module.
- Tests importing from src/legacy/.
- Direct fetch() instead of src/lib/http.ts (auth, retries, tracing).

A path-scoped rule (loaded only when working on matching files fact; after compaction it is reloaded on demand, so don’t put anything critical for the whole session here):

---
paths:
  - "src/api/**/*.ts"

# API rules
- Validate bodies with zod schemas in src/api/schemas/; never hand-roll checks.
- New endpoint = handler + schema + openapi.yaml entry + test in src/api/__tests__/ + touchpoint entry if it emits events.

What matters here fact:

  • deny applies in every mode, including auto and bypassPermissions; Read(./.env) also catches cat .env. Forbidding edits to the linter config and to the hooks themselves protects against the model’s temptation to “raise the limit to 100 lines, that’s enough” (this behavior is documented in community reports). Changing the config — human decides.
  • A Stop hook with exit 2 sends Claude back to work with the text from stderr; after 8 consecutive blocks without tool calls, Claude Code ends the turn anyway (the cap is raised via CLAUDE_CODE_STOP_HOOK_BLOCK_CAP).
  • Hooks in .claude/settings.json start working for teammates only after they trust the folder (workspace trust).
  • notify-send is Linux; on macOS, replace it with osascript -e 'display notification …'.

4.4 Hook scripts (.claude/hooks/)

All scripts read the event JSON from stdin, write the reason to stderr and return exit 0 (no objections) or 2 (block / send Claude back to work). Make them executable: chmod +x .claude/hooks/*.sh. Requires jq.

format.sh — formatting after every edit (silent on success):

#!/usr/bin/env bash
# PostToolUse(Edit|Write): format the edited file. Silent on success.
f=$(jq -r '.tool_input.file_path // empty'); [ -z "$f" ] && exit 0
case "$f" in
  *.ts|*.tsx|*.js|*.jsx|*.json|*.css|*.md) npx prettier --write --log-level warn "$f" >/dev/null 2>&1 || true ;;
  *.py) ruff format -q "$f" >/dev/null 2>&1; ruff check --fix -q "$f" >/dev/null 2>&1 || true ;;
esac
exit 0

related-tests.sh — only related tests, output only on failure (cures “slow tests”):

#!/usr/bin/env bash
# PostToolUse(Edit|Write): run tests related to the edited source file; report only failures.
f=$(jq -r '.tool_input.file_path // empty'); [ -z "$f" ] && exit 0
cd "$CLAUDE_PROJECT_DIR" || exit 0
case "$f" in
  */node_modules/*|*.test.*|*.spec.*|*.md|*.json|*.css) exit 0 ;;
  *.ts|*.tsx|*.js|*.jsx)
    if ! out=$(npx vitest related --run --reporter=dot --passWithNoTests "$f" 2>&1); then
      echo "$out" | grep -E "FAIL|×|✗|Error|AssertionError|expected" | head -60 >&2
      echo "Related tests failed for $f. Fix the cause before continuing." >&2
      exit 2
    fi ;;
  *.py)
    if ! out=$(pytest --testmon -q -x 2>&1); then echo "$out" | tail -40 >&2; exit 2; fi ;;
esac
exit 0

For Jest: npx jest --findRelatedTests "$f" --passWithNoTests --silent. For Go: go test ./$(dirname "$f")/.... For Rust: cargo test -p <crate>. If related tests take longer than ~10 seconds, that is a signal to fix the test structure (section 8), not to disable the hook.

protect-files.sh — the second line of defense (the first is deny in settings):

#!/usr/bin/env bash

5. Rules for writing rules

5.1 What goes where

Mechanism When it loads Survives compaction What it is for What it is NOT for
CLAUDE.md every session, in full yes (re-read from disk) verification commands, gotchas, decisions not in the code, things corrected twice architecture, folder structure, 30-line procedures, personal preferences
.claude/rules/*.md without paths every session yes “always” rules split by topic things needed only in one part of the code
.claude/rules/*.md with paths when reading/editing matching files no (reloaded on demand) rules for one subsystem rules that must apply for the whole session
Skill description — always; body — on invocation body is re-inserted (≤ 5k tokens/skill) procedures, references, workflows with a /command “always do X”
Subagent on invocation — noise isolation, parallelism, a fresh look, restricted permissions “a better answer” (it doesn’t give one), short edits
Hook on an event takes up no context everything that must happen every time preferences with exceptions
permissions.deny / sandbox always — “never” (secrets, migrations, generated code) —
Output style the whole session yes tone/format of responses facts about the project
Auto memory (MEMORY.md) every session (first 200 lines / 25 KB) yes your corrections and preferences that Claude recorded itself team rules (they belong in CLAUDE.md)

Anti-patterns from Anthropic’s article “Steering Claude Code” fact: “every time X happens, do Y” in CLAUDE.md (→ hook); “never do Z” in CLAUDE.md (→ deny/hook); a 30-line procedure in CLAUDE.md (→ skill); an API rule without paths (→ path-scoped); personal preferences in the project file (→ ~/.claude/CLAUDE.md or CLAUDE.local.md).

5.2 How to phrase rules

  • Verifiable: “2-space indentation”, “run pnpm test:unit before committing”, “handlers live in src/api/handlers/” — not “format properly”, “test your changes”, “keep files organized”. fact
  • Short and structured: headings + bullets; Claude resolves contradictions between files arbitrarily — clean them up periodically (/doctor prompt-audit).
  • No “IMPORTANT”, “ALL CAPS”, “think hard”, “don’t be lazy”, “loop until done” — on current models this leads to over-applying the rule or overthinking, not obedience. fact Reasoning depth is controlled with /effort and the word ultrathink for a single turn.
  • Comments for humans inside CLAUDE.md go in <!-- … -->: Claude Code strips them before loading into the context. fact
  • A line you repeat to the model for the third time is not an instruction but a defect in the system: either the file is too long (the line gets lost), or the rule has no exceptions (→ hook).

5.3 The lifecycle of a rule

  1. A mistake is noticed → a row in docs/rules/common-mistakes.md (Seen = 1) and, if appropriate, in 20-mistakes.md.
  2. After every correction, finish with Boris Cherny’s phrase: “Update your CLAUDE.md so you don't make that mistake again” — Claude is good at writing rules for itself practice; you then “ruthlessly edit” the file.
  3. Seen = 2 → promotion into the deterministic layer: a lint rule, a hook, an entry in touchpoints.json, a deny rule. The line in CLAUDE.md is then deleted — otherwise the file keeps growing.
  4. Once a month: /doctor (cut what the model would find anyway) and /doctor prompt-audit (outdated and contradictory items). After a new model is released — a review: some workaround rules become unnecessary. fact

6. A clean-code standard and how to enforce it

Your requirement is a “perfectionist’s paradise”: English comments, a single format, OOP, everything extracted, decent names, no 1000-line files. This is achievable only if the standard lives in the linter and formatter config, and the rules merely link to it. The model follows a linter that returns errors to it very well, and a paragraph about “write clean code” poorly.

6.1 Principles (in docs/rules/code-style.md)

Karpathy’s four rules for agents practice (January 2026; packaged by the community as a CLAUDE.md file): think before coding (state assumptions, ask, don’t guess), simplicity first (the minimum code that solves the task, no abstractions “for the future”), surgical changes (every changed line traces back to the request; don’t “tidy up” neighboring code), verifiable goals (test first, then implementation).

Plus the project standard:

Area Rule Why
Language Identifiers, comments, docstrings, commit messages, PRs — English only one language = one “axis” for grep; i18n is separated from code
Size file ≤ 300 lines (UI component ≤ 400), function ≤ 50, class ≤ 200, cyclomatic complexity ≤ 10, nesting ≤ 4, parameters ≤ 4, one exported class per file the model and the human read the module whole; small files are cheaper in the context and conflict less often in worktrees
Naming full words; booleans are predicates (isActive); functions are verbs; types are nouns; the file is named after its export (user-repository.ts ↔ UserRepository) searching by name = searching by meaning
Comments explain why, not what; no commented-out code; TODO only with an issue number the “what” is already said by the code; clutter confuses the model
Structure one module = one reason to change; dependencies point inward (ui → app → domain ← infra); “feature folders” OOP/layering without dogma; easy to extract
Errors never swallowed; a single helper; no empty catch the model likes to “suppress” an error to make a test pass
Dead code deleted, not commented out; knip / ruff F401 are clean the model tries to use dead code
Suppressions no eslint-disable / noqa / @ts-ignore without explicit human approval otherwise the limits are meaningless

6.3 Legacy: a ratchet, not a big bang

If you turn the limits on as error on old code, the linter goes red on hundreds of files and the model starts “fixing” the wrong things. The scheme teams use practice:

  1. The limits are turned on as error for new files and for all of src/**, but existing offenders are listed in an override block with a relaxed limit (for example, max-lines: 800 for 11 specific files).
  2. A “no new violations” rule: stop-gate.sh compares the number of violations with a baseline file (lint-baseline.json) and fails if it has grown.
  3. Once a quarter (or every Friday) — /batch split every file in lint-baseline over 300 lines into cohesive modules in separate worktrees + /split-file by hand for the hard cases. The list in the override block shrinks; once it is empty, the block is deleted.
  4. Non-English comments: once, /batch translate all non-English comments in src/ to English, keep meaning, do not touch code (after that — a hook check, for example rg -n "\p{Cyrillic}" src --type ts in stop-gate.sh).

6.4 Playbook: “split a 1000-line file”

  1. Characterization. A list of exports and all callers (rg), whether public behavior has tests. No tests — characterization tests first (they pin the current behavior, even if it is odd).
  2. Responsibility map. Group by “reason to change”: parsing, validation, data access, orchestration, output formatting. Each group → a file ≤ 300 lines named after its export. The human approves the map.
  3. Mechanical move. Cut and paste, update imports (ast-grep for bulk import rewrites), a barrel index.ts only if there are many callers.
  4. Verification. typecheck, lint, related tests, knip. Behavior doesn’t change; no “improvements along the way” in the same PR.
  5. Locking it in. The file disappears from lint-baseline; /simplify as a separate pass, if you want.

This is what /split-file (section 4.6) is for; for dozens of files — /batch with the same description (5–30 units in isolated worktrees, one PR each fact).

7.2 How to write a spec so the model doesn’t “shrink” it

  • The phrase be ambitious in the prompt fact: by default the model reads the task conservatively and does the minimum; if you need empty/error states, keyboard navigation, persistence — list them as scope, not as “think harder”.
  • Acceptance criteria — as test names. That is the spec, the test plan and the Definition of Done at the same time. The reviewer checks exactly these.
  • The “Touchpoints affected” section is filled from the map (7.3). An empty section when a shared concept changes = the spec isn’t ready.
  • Claude writes the plan from plan mode into a file that is re-inserted after compaction fact — one more reason to keep the plan on disk and not in the chat.

scripts/check-touchpoints.ts (≈ 40 lines, no dependencies; pnpm check:touchpoints = node --experimental-strip-types scripts/check-touchpoints.ts or tsx):

// Fails when a member of a shared concept is missing from any of its registries.
import { readFileSync, existsSync } from "node:fs";

type Registry = { file: string; pattern: string };
type Rule = { name: string; source: string; memberRegex: string; registries: Registry[]; fileExists?: string };

const rules: Rule[] = JSON.parse(readFileSync("docs/rules/touchpoints.json", "utf8"));
let failures = 0;

for (const rule of rules) {
  const source = readFileSync(rule.source, "utf8");
  const members = [...source.matchAll(new RegExp(rule.memberRegex, "gm"))].map((m) => m[1]);
  for (const member of members) {
    for (const reg of rule.registries) {
      const text = existsSync(reg.file) ? readFileSync(reg.file, "utf8") : "";
      if (!new RegExp(reg.pattern.replaceAll("{member}", member)).test(text)) {
        console.error(`[${rule.name}] "${member}" is missing in ${reg.file}`);
        failures += 1;
      }
    }
    if (rule.fileExists) {
      const path = rule.fileExists.replaceAll("{member_lower}", member.toLowerCase());
      if (!existsSync(path)) { console.error(`[${rule.name}] "${member}": expected file ${path}`); failures += 1; }
    }
  }
}
if (failures > 0) { console.error(`${failures} touchpoint gap(s). See docs/rules/touchpoints.md`); process.exit(1); }
console.log("touchpoints: ok");

11.3 Creating a skill: TDD for documentation

The main rule of superpowers writing-skills practice: “no skill without a failing test”. A skill is not a story about how you once solved a task, but a proven technique that a future Claude will find and apply.

Phase What you do How you check it
RED — baseline You give the task scenario to a fresh subagent without the skill. You record where it went wrong and how it justified itself (“updating the enum is enough, the rest is out of scope”) claude -p or a general-purpose subagent; save the transcript in evals/
GREEN — minimum You write SKILL.md: a “what + when” description, the body — steps, checks, “done when…”. You repeat the scenario with the skill the subagent follows the steps; the done-check passes
REFACTOR You close the loopholes found in the runs; remove narrative; body < 500 lines; reference material goes to references/, deterministic parts to scripts/ repeat on 2–3 variations of the scenario
Evals skill-creator (/plugin install skill-creator@claude-plugins-official): test cases in evals/evals.json, each in an isolated subagent, grades in grading.json, a benchmark across iterations; description optimization on ~20 trigger/non-trigger queries for up to 5 rounds fact “evaluate my add-notification-type skill with skill-creator”
Ship project — .claude/skills/<name>/ in git; personal — ~/.claude/skills/; several projects — a plugin (<plugin>/skills/, .claude-plugin/plugin.json, your own marketplace repository, claude plugin validate) /reload-skills, /skills
Observe after 2 weeks, /skill-doctor: never invoked → fix the description or delete it —

A recipe-skill template — the most common form for your pains: “the same multi-step operation”. An example for the notification system that walks through the touchpoints map step by step:

---
name: add-notification-type
description: Add a new notification type across every consumer (routing, template, i18n, prefs UI, admin filter, analytics, tests, docs). Use when a new notification/event type is requested.
when_to_use: "new notification", "add notification type", "notify users when", "digest/alert/reminder type"
arguments: [type_name]
argument-hint: [TYPE_NAME_IN_UPPER_SNAKE]
allowed-tools: Read, Edit, Grep, Glob, Bash(pnpm check:touchpoints), Bash(pnpm vitest *), Bash(rg *)
---
## Context (live)
- Existing types: !`rg -n "^\s+[A-Z_]+\s*=" src/notifications/types.ts | head -40`
- Consumers map: see docs/rules/touchpoints.md → NotificationType

## Procedure for $type_name
1. Pick the closest existing sibling type and `rg -n "<SIBLING>" src docs` — every hit is a place to mirror.
2. Add the enum member, then mirror the sibling in each consumer from the map (routing, template + i18n keys,
   prefs label, admin filter, analytics payload). Do not skip "irrelevant" consumers — register with an explicit no-op if needed.
3. Tests: copy the sibling's test file, adapt; run `pnpm vitest related --run` on touched files.
4. Docs: add the row to docs/notifications.md.
5. Done when: `pnpm check:touchpoints` passes, related tests green, and you show the list of files changed vs the map.

The same skeleton (live context → procedure following the map → done-check) works for /add-endpoint, /add-flag, /new-migration, /add-permission, /onboard-module.

What makes a skill bad practice: a description with process details instead of “when” (the model doesn’t find it at the right moment); narrative about a single case; a duplicate of what is already in CLAUDE.md; “always do X” (that’s a hook); 1,200 lines of reference in the body instead of references/; dozens of skills of which three ever get invoked.

11.4 Creating an agent

When to make an agent rather than a skill with context: fork: when it is a role that will be invoked many times, with its own memory, toolset and report format (a reviewer, an auditor, a test runner). A one-off isolated procedure is a skill with fork.

The order fact:

  1. /agents → create → “Generate with Claude”: you describe the role in words, Claude writes the file; then you edit it by hand: description must answer “when to delegate” (the phrase “Use proactively when …” makes delegation automatic), tools — the minimum (Read, Grep, Glob for read-only), model — haiku for search, sonnet for routine work, inherit for judgment, memory: project if the role should learn.
  2. The agent’s system prompt is like those of reviewer/scout/test-runner in 4.5: role, inputs, a 3–5 step procedure, an output format with a line limit, what not to do.
  3. Test it like a skill: scenario → baseline with general-purpose → run with the new agent → compare; the agent is good if its output is usable right away without clarifications.
  4. After two weeks — /usage: if the agent eats more than it saves, cut down its model or its output.

Candidates that pay off for almost everyone (start with 3, not 10):

Agent Role Model / tools Memory
reviewer spec compliance + systemic completeness inherit · Read, Grep, Glob project
scout collecting files and entry points haiku · Read, Grep, Glob —
test-runner a full run, failures only sonnet · Bash, Read, Grep —
i18n-auditor hardcoded strings, missing keys, pluralization haiku · Read, Grep, Glob, Bash(rg *) project (knows the exceptions)
migration-runner apply/roll back migrations in a worktree, compare the schema sonnet · Bash(pnpm db:*), Read —

11.5 The “pattern → skill/agent” pipeline inside the system

For this to work without heroics, the pipeline is built into rituals and files that already exist:

  1. Capture — any of the signals from 11.2 → a row in pattern-candidates.md (Count = 1). Claude does this itself at the end of a task if you add a step to /compound: “if this type of task has come up before (grep by docs/solutions tags), update the candidate ledger”.
  2. Threshold — Count ≥ 3 or (Count ≥ 2 and minutes × Count ≥ 30) → a candidate for Friday.
  3. /promote idea — a skill that reads both ledgers and docs/solutions/, proposes a form for every candidate over the threshold using the decision tree, drafts the file and a baseline-test plan; it waits for your “ok” before writing:
---
name: promote
description: Turn repeated patterns from docs/rules/pattern-candidates.md and common-mistakes.md into skills, agents, hooks or rules. Reports proposals; writes files only after approval.
disable-model-invocation: true
---
1. Read docs/rules/pattern-candidates.md, docs/rules/common-mistakes.md and the tags in docs/solutions/*.md.
2. For every row with Count ≥ 3 (or Count ≥ 2 and Count × minutes ≥ 30) and Status ≠ shipped:
   decide the form with the decision tree in the manifest (hook → skill → agent → workflow → routine → personal).
3. Draft: the file (SKILL.md / agent .md / hook + settings entry / rule), a 3-line baseline scenario for the RED phase,
   and the eval cases for skill-creator. Show all drafts in one message. Do not write files yet.
4. After approval: write files, run the baseline and the skill/agent scenario in subagents, report the difference,
   set Status = shipped with the date, and remove the now-redundant lines from CLAUDE.md or rules.
  1. The skill garden — once a quarter: /skill-doctor + the ledger → delete what isn’t invoked, merge duplicates, update descriptions; the rule is “≤ 15 model-visible skills per project, names are verbs, each has an owner and a date of last usefulness”.
  2. Sharing — skills that have taken root in two projects move into your own plugin (~/dev/my-claude-plugin with marketplace.json); it installs into every new project with one command, and you build up a personal “library of hands”.

Pipeline metrics (added to section 16): the number of skills/agents; the share invoked in 30 days; candidates older than 3 weeks that haven’t been given a form (“pattern debt”); an estimate of minutes saved = Count × minutes per repetition.

12. Token economics and the cache

12.1 How the bill is calculated fact

  • Every turn sends the whole conversation again; the prompt cache makes the repeat cheap as long as the prefix is unchanged and the cache is warm. On a subscription, the main conversation keeps the cache for 1 hour, subagents and API keys for 5 minutes (promptCacheTtl, subagentPromptCacheTtl = 1h change this).
  • The order of request layers: system prompt + tools → CLAUDE.md/auto memory/unscoped rules → conversation. A change in an upper layer invalidates everything below it.
  • A 1M-token context on Opus 5.5 / Sonnet 5.5 / Haiku 5.5 / Fable; autocompaction near the ceiling; after > ~54 min of idle time on a conversation > 200K, Claude Code compacts on its own so as not to lose the warm cache. Compaction is also a big request (it reads the whole conversation), especially on a cold cache.
  • /usage shows the share of skills / subagents / plugins / MCP servers and the cache hit rate, and gives recommendations (the f key applies the ones it can). /context — what is taking up the window right now. /insights — an HTML report on your habits over recent sessions.

12.2 What breaks the cache and what doesn’t fact

Breaks it (one expensive turn) Doesn’t break it
switching the model (/model, opusplan on entering/leaving plan mode) editing repository files
changing effort on older models (not on Opus/Sonnet/Haiku 5.5 and Fable 5.1) editing CLAUDE.md mid-session (it won’t apply until /clear//compact)
turning on fast mode changing the permission mode
connecting/disconnecting an MCP server or a plugin with MCP; denying a whole tool invoking skills and commands (they are inserted as messages)
compaction (by design) /rewind (truncates to an already cached prefix)
accumulating many images /recap, changing the output style
updating Claude Code (a new system prompt) spawning a subagent (it has its own cache; fork reads the parent’s)

12.3 Savings rules (in order of payoff)

  1. /clear between unrelated tasks — free and the biggest effect; /clear oauth-migration names the session so you can come back with --resume. fact
  2. A short starting context: CLAUDE.md ≤ 60 lines, path-scoped rules, skills with disable-model-invocation, turn off unused MCP servers (/mcp) and skills (/skills, /skill-doctor). The goal is a starting context < 15–20k tokens (check /context in an empty session) idea.
  3. Prefer CLI over MCP: gh, aws, sentry-cli don’t add per-tool descriptions; MCP tools are deferred anyway (tool search), but every server adds names and instructions fact.
  4. LSP instead of reading files: one “go to definition” instead of grep + reading several candidates; type diagnostics arrive after an edit without running the compiler fact.
  5. Noise goes to subagents: a full test run, logs, a broad search. Only a summary comes back.
  6. Output filters: the filter-test-output.sh hook; RTK (section 13) cuts the output of git, pnpm, vitest, docker, kubectl by 60–90% practice.
  7. /compact with a focus, at a natural pause (“/compact keep the API changes and test commands”), instead of waiting for autocompaction in the middle of a task; /rewind instead of compaction if a branch of the conversation turned out to be a dead end fact.
  8. Model and effort — at the start, Haiku for scouting, Sonnet for routine work.
  9. Specific prompts: “users complain that login fails after a timeout; look at refresh in src/auth/, write a failing test, then fix it” instead of “fix the login”. Saves a round of edits fact.
  10. Watch the background: /loop, /goal check-ins, cross-session messages and lingering subagents send requests while you aren’t typing fact.
  11. Caveman (optional): a terse output mode, −65% output tokens on average, but +1–1.5k input tokens per turn; on short sessions it can end up a net loss — measure it practice.
  12. A statusline with context and cost (/statusline), so the counter is always in view.

A money benchmark fact: in enterprise deployments the average cost is ≈ $13 per developer per active day, $150–250 a month; 90% of users spend < $30 a day. On Pro/Max, “effort” is what gets counted, but the same rules stretch the limits.

18.1 Types instead of scripts: exhaustiveness and “generate, don’t synchronize”

check-touchpoints (7.3) is a safety net for what can’t be expressed in types. But most registries can be expressed in types, and then a missing consumer is caught by the compiler even before the hook — the cheapest and most reliable form of “systematic” changes practice.

TypeScript — a registry as Record<Enum, …> and assertNever in a switch:

// src/notifications/types.ts
export const NOTIFICATION_TYPES = ["INVOICE_PAID", "COMMENT_REPLY", "WEEKLY_DIGEST"] as const;
export type NotificationType = (typeof NOTIFICATION_TYPES)[number];

// src/notifications/channels.ts — adding a type without a route is a type error
export const CHANNEL_BY_TYPE = {
  INVOICE_PAID: ["email", "push"],
  COMMENT_REPLY: ["push"],
  WEEKLY_DIGEST: ["email"],
} satisfies Record<NotificationType, readonly Channel[]>;

// src/notifications/render.ts — a missing case is a type error
export function render(n: Notification): Rendered {
  switch (n.type) {
    case "INVOICE_PAID": return renderInvoice(n);
    case "COMMENT_REPLY": return renderReply(n);
    case "WEEKLY_DIGEST": return renderDigest(n);
    default: return assertNever(n.type);
  }
}
export function assertNever(x: never): never { throw new Error(`Unhandled case: ${String(x)}`); }

Python — Enum + match + assert_never under pyright/mypy (strict, --warn-unreachable):

from enum import Enum
from typing import assert_never

class NotificationType(Enum):
    INVOICE_PAID = "invoice_paid"
    COMMENT_REPLY = "comment_reply"
    WEEKLY_DIGEST = "weekly_digest"

CHANNELS: dict[NotificationType, tuple[str, ...]] = {  # completeness checked by scripts/check-touchpoints (dict cannot be exhaustive)
    NotificationType.INVOICE_PAID: ("email", "push"),
    NotificationType.COMMENT_REPLY: ("push",),
    NotificationType.WEEKLY_DIGEST: ("email",),
}

def render(kind: NotificationType) -> str:
    match kind:
        case NotificationType.INVOICE_PAID: return render_invoice()
        case NotificationType.COMMENT_REPLY: return render_reply()
        case NotificationType.WEEKLY_DIGEST: return render_digest()
        case _: assert_never(kind)  # type checker fails when a member is unhandled

The second principle is generate, don’t synchronize: one source of truth and codegen instead of N places you have to remember. A Zod/Pydantic schema → types → OpenAPI → client; a Prisma/Drizzle schema → DB types; an enum → i18n keys via a script that fails if a key is missing. Every generated artifact is a touchpoint you no longer have to remember. Whatever stays outside types and generation (documentation, admin lists, analytics) goes into touchpoints.json.

A rule in 00-workflow.md idea: “Adding a shared concept? Prefer a typed registry (satisfies Record<…>, assert_never) over a free-form map; if a consumer cannot be typed, register it in touchpoints.json.”

18.2 Spec ↔ tests: acceptance criteria as an executable contract

In the spec, acceptance criteria are written as test names (7.2). Close the loop with a script that checks that every criterion exists as a test and passes — and the Stop hook won’t let Claude go until the spec is “green” idea:

// scripts/check-spec-tests.ts — every "- [ ] `test name`" in the active spec must exist in a test file.
import { readFileSync, readdirSync, statSync } from "node:fs";
import { join } from "node:path";

const spec = process.argv[2] ?? latestSpec();
const criteria = [...readFileSync(spec, "utf8").matchAll(/^- \[[ x]\] `([^`]+)`/gm)].map((m) => m[1]);
const testFiles = walk("src").filter((f) => /\.(test|spec)\.[tj]sx?$/.test(f));
const corpus = testFiles.map((f) => readFileSync(f, "utf8")).join("\n");
const missing = criteria.filter((c) => !corpus.includes(c));
if (missing.length) {
  console.error(`Spec ${spec}: ${missing.length} acceptance criteria have no test:`);
  missing.forEach((m) => console.error(`  - ${m}`));
  process.exit(1);
}
console.log(`spec-tests: ${criteria.length} criteria covered`);

function walk(dir: string): string[] {
  return readdirSync(dir).flatMap((n) => { const p = join(dir, n); return statSync(p).isDirectory() ? walk(p) : [p]; });
}
function latestSpec(): string {
  const dir = "docs/specs";
  return join(dir, readdirSync(dir).filter((f) => f.endsWith(".md") && f !== "TEMPLATE.md")
    .sort((a, b) => statSync(join(dir, b)).mtimeMs - statSync(join(dir, a)).mtimeMs)[0]);
}

The test is named exactly like the criterion: it("notifications: creates a digest when the user has more than 5 unread", …). Add run spec-tests pnpm -s check:spec-tests to stop-gate.sh, and run the tests themselves by name with vitest -t "<name>" in /feature. The spec status changes to implemented only when the script is green.

18.3 One gate in three places + secrets + commits

Right now the checks live in Claude hooks. Humans and CI must check the same thing, with the same script, otherwise the standard drifts apart:

#!/usr/bin/env bash
# scripts/gate.sh — the single quality gate. Used by: Claude Stop hook, lefthook pre-push, CI.
set -euo pipefail
npx tsc --noEmit
npx eslint . --max-warnings 0 --cache
pnpm -s check:touchpoints
pnpm -s check:spec-tests || true          # advisory until the spec is marked implemented
npx knip --no-progress
npx depcruise src --config .dependency-cruiser.cjs
gitleaks protect --staged --redact --no-banner
  • lefthook (lefthook.yml): pre-commit → formatter + gitleaks protect --staged + commitlint; pre-push → scripts/gate.sh. One file, works for everyone and in every worktree.
  • CI — the same scripts/gate.sh + the full test suite; branch protection on main.
  • Claude — stop-gate.sh calls scripts/gate.sh instead of its own list.
  • gitleaks closes the most expensive class of autonomous-agent mistakes — a secret in a commit; add Read(./.env*) to deny (already there) and gitleaks to the gate.
  • Conventional commits (commitlint + a rule in 00-workflow.md: feat(notifications): add weekly digest) → changesets or semantic-release generate the changelog and versions; Claude writes such messages without reminders if the format is checked by a hook.

18.5 Semantic gates: prompt and agent hooks

Hooks are not only shell commands fact: type: "prompt" sends the event input to a cheap model and gets a decision back as JSON; type: "agent" launches a subagent with Read/Grep/Glob that verifies the condition against the files (experimental). The default timeouts are 30 and 60 seconds; $ARGUMENTS is the event JSON. This covers checks that can’t be expressed as a script:

{
  "hooks": {
    "Stop": [
      { "hooks": [
        { "type": "prompt", "model": "haiku",
          "prompt": "You are a release gate. Input is the final assistant turn: $ARGUMENTS. Decide whether the turn shows evidence (actual command output) for tests, typecheck and lint, and lists remaining [?] items from the spec. If evidence is missing, block with a one-line reason telling the assistant what to run." }
      ] }
    ],
    "UserPromptSubmit": [
      { "hooks": [
        { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/contract-reminder.sh" }
      ] }
    ]
  }
}

contract-reminder.sh idea — if the prompt contains words like add|new|type|event|route|flag|notification, it prints one line to stdout: “Shared concept likely affected: fill the task contract and read docs/rules/touchpoints.md first” — and that line lands in the context next to your prompt (additionalContext). Cheap, and it hits the “unsystematic changes” pain dead on. Take the exact response schema for a prompt hook from the hooks reference (the Prompt-based hooks section) when you roll it out — it is short.

18.6 Sandbox + auto mode

The sandbox is an OS boundary around Bash (Seatbelt on macOS; bubblewrap + socat on Linux/WSL2): writes only to the working directory and --add-dir, network through a local proxy with the sandbox.network.allowedDomains allowlist, protected paths (.claude, hooks, shell profiles) closed for writing fact. The main effect is auto-allow: commands inside the sandbox run without permission prompts even in manual mode; auto mode and the sandbox stack up (the classifier decides, the OS restricts).

{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "network": { "allowedDomains": ["registry.npmjs.org", "pypi.org", "files.pythonhosted.org", "github.com", "api.github.com"] },
    "credentials": { "files": { "mode": "deny", "patterns": ["~/.ssh/**", "~/.aws/**"] } },
    "excludedCommands": ["docker compose *"]
  }
}

Turn it on with /sandbox (saves to .claude/settings.local.json) or the sandbox key in settings. Limitations fact: Read/Edit/WebFetch, hooks, MCP and LSP run outside the sandbox (permission rules hold them in check); tools without proxy support (ssh, many DB drivers) won’t reach the network — use narrow excludedCommands patterns for them.

18.7 Startup briefing + /handoff

after-compact.sh (4.4) only runs after compaction. Add a briefing on every startup and resume — a SessionStart hook with startup|resume matchers prints the state, and Claude starts from it rather than from “what have we got here” fact:

#!/usr/bin/env bash
# .claude/hooks/briefing.sh — SessionStart(startup|resume): state of the world in ≤ 25 lines.
input=$(cat); cd "$CLAUDE_PROJECT_DIR" || exit 0
src=$(echo "$input" | jq -r '.source')
echo "Session briefing ($src). Branch: $(git branch --show-current 2>/dev/null). Dirty files: $(git status --porcelain | wc -l | tr -d ' ')."
h=$(ls -t docs/handoff/*.md 2>/dev/null | head -1); [ -n "$h" ] && { echo "Last handoff: $h"; sed -n '1,15p' "$h"; }
p=$(ls -t docs/plans/*.md 2>/dev/null | head -1); [ -n "$p" ] && { echo "Open plan items in $p:"; grep -c "^- \[ \]" "$p"; }
if [ "$src" = "resume" ]; then
  exp=$(echo "$input" | jq -r '.prompt_cache_likely_expired // empty'); cost=$(echo "$input" | jq -r '.estimated_cache_write_usd // empty')
  [ "$exp" = "true" ] && echo "Note: prompt cache likely expired; re-sending context costs ≈ \$$cost. Consider /clear + handoff if the old context is not needed."
fi
exit 0

/handoff is an end-of-session skill (or called from /compound): it writes docs/handoff/<date>-<branch>.md — what was done, what is left, which decisions were made, which commands were run, what is broken. On resume, Claude Code passes the hook seconds_since_last_response, context_tokens, prompt_cache_likely_expired, estimated_cache_write_usd fact — so the briefing can say outright “it is cheaper to start from the handoff than to bring back 180k tokens of cold context”.

18.8 CI agent: claude-code-action

The official anthropics/claude-code-action@v1 runs Claude Code in GitHub Actions fact. Three scenarios that pay off immediately practice:

# .github/workflows/claude.yml
name: claude
on:
  pull_request: { types: [opened, synchronize, ready_for_review] }
  issue_comment: { types: [created] }
permissions: { contents: write, pull-requests: write, issues: write, id-token: write }
concurrency: { group: claude-${{ github.event.pull_request.number || github.event.issue.number }}, cancel-in-progress: true }
jobs:
  review:
    if: github.event_name == 'pull_request' && !github.event.pull_request.draft
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          claude_args: "--model sonnet --max-turns 12"
          prompt: |
            Review this PR against docs/specs/ (find the spec by branch name) and docs/rules/.
            Report only correctness, missing touchpoints (docs/rules/touchpoints.md) and untested acceptance criteria.
            Post one structured comment; do not restate the diff; do not comment on style (lint owns it).
  fix:
    if: github.event_name == 'issue_comment' && contains(github.event.comment.body, '@claude fix')
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          claude_args: "--max-turns 25"
          prompt: |
            Fix the issue described in #${{ github.event.issue.number }} following .claude/rules/00-workflow.md.
            Write the failing test first, make scripts/gate.sh pass, open a PR with the evidence.

Plus a nightly job “if main is red — find the cause, fix it, open a PR” and a morning issue triage (labels + a draft spec in docs/specs/). Rules: the sonnet model for review, --max-turns, concurrency per PR, secrets only via GitHub Secrets, a ## CI rules section in CLAUDE.md (“don’t push to main, don’t change workflows, only comment”). The action reads the same CLAUDE.md and rules as the local session — there is one standard.

18.9 Monitor, Remote Control, PushNotification, Channels

  • Monitor fact — a built-in tool: Claude runs a command in the background and receives every line of output as an event (tailing logs, polling PR/CI status, watching a directory, a WebSocket). A 5-minute deadline by default, 30 at most. Prompts that save waiting: “monitor the dev server log and fix the first stack trace you see”, “watch gh pr checks --watch and tell me when it is green or what failed”, “monitor vitest in watch mode while I describe the next task”.
  • Remote Control (/remote-control) fact — continue a local session from your phone via the Claude app; PushNotification sends a push to your phone when Remote Control is connected — “ping me when the batch finishes”. If you work from your phone, this replaces “sitting at the terminal”.
  • Channels (research preview, v2.1.80+) fact — Telegram/Discord/iMessage and webhooks push events into an already running session: a message from CI, an alert, your command from a chat. The difference from Remote Control: there you drive the session, here the world notifies the session. Set it up when you want “CI failed → the session started fixing it on its own”.
  • Dispatch — the same for the desktop app (QR code → the phone as a remote).

18.10 Coordinating parallel sessions

  • Cross-session messaging (SendMessage / ListAgents, v2.1.224+) fact: sessions in different worktrees can send each other messages — “API changed: createDigest now takes userId first” — and get notified when another session goes idle. With a 3–5 worktree layout, this removes the manual “carrying news” between tabs.
  • isolation: worktree on a subagent fact — each subagent works in its own worktree; parallel edits don’t conflict; handy for /batch-like tasks within one session.
  • Session cron (CronCreate, /loop with a self-adjusting interval via ScheduleWakeup) fact — “every 10 minutes check CI and, if it’s red, deal with it”; lives as long as the session lives, restored on --resume.
  • EnterWorktree/ExitWorktree — Claude creates a worktree for a risky edit by itself and comes back; ask it to “do this in a fresh worktree”.

18.11 A project template and versioning the “OS” itself

  • A template repository claude-os-template with the whole structure from section 4 (CLAUDE.md skeleton, rules, hooks, settings, docs templates, gate.sh, lefthook, dependency-cruiser, workflows). A new project: gh repo create <name> --template <you>/claude-os-template → /bootstrap-project (a skill that replaces the stack and command placeholders, reads package.json, enables the LSP plugin). “Super-clean in every project” stops depending on memory.
  • A personal plugin ~/dev/claude-os-plugin (skills /spec, /feature, /split-file, /promote, agents, hooks) with marketplace.json — one install command in any repo; versions in plugin.json.
  • ~/.claude in git (dotfiles/chezmoi): settings.json, CLAUDE.md, rules/, skills/ — a change history of your rules; roll back if a new rule made the behavior worse.
  • docs/CHANGELOG-claude-os.md in the project: date → what changed in the rules/hooks → why. Without it you can’t link a shift in the metrics (section 16) to a specific change.
  • A/B testing of rules practice: a CLAUDE.md variant is tested like a skill — 5–10 typical tasks via claude -p --bare --append-system-prompt-file <variant> on fresh worktrees, comparing the number of corrections and gate pass rates. superpowers shows such a test campaign for CLAUDE.md variants.

18.12 Vendoring library documentation

For the 5–8 libraries where Claude most often gets the API wrong (ORM, auth, UI kit, payment SDK), put a digest of the current documentation for the version you use in docs/vendor/<lib>@<version>/*.md (via defuddle from obsidian-skills or an export from Context7) and add a path-scoped rule: “for <lib>, read docs/vendor/<lib>@<version>/ before using an API you are not sure about”. The effect: fewer invented methods, fewer WebFetch tokens, one version for all sessions and for the CI agent; /ingest of these files into the wiki yields cross-project tool pages with a check date (9.3). Updating — a monthly routine compares the version in the lockfile with the folder.

18.13 Deeper tests: property-based, mutation, /bisect

  • Property-based (fast-check for TS, hypothesis for Python): the model writes example-based tests very well and edge cases poorly; a property (“serialize ∘ deserialize = id”, “the shares sum to 100%”) finds them for it. A rule in tests.md: “for pure functions with non-trivial input — at least one property test”.
  • Mutation testing (Stryker / mutmut) once a month in a routine: it reveals tests that check nothing (both the model and a human on a deadline love to write those).
  • /bisect — a skill: “write a failing test for the regression → git bisect run pnpm vitest run <file> → name the commit → explain the cause → propose a fix”. A classic that agents do faster than humans because they don’t get lazy.

18.14 Machine-readable output

Everything Claude or a hook reads should be able to speak JSON: vitest --reporter=json --outputFile, eslint -f json, tsc --pretty false, pytest --json-report, structured application logs (pino / structlog), claude -p --output-format json in scripts. Hooks parse fields instead of grepping a wall of text, Claude gets facts (failed: 2, first: file:line) instead of 400 lines, and filter-test-output.sh becomes trivial. This complements RTK/Caveman from section 12; it doesn’t replace them.

18.15 The “issue → spec → PR” and “prod → test → PR” loops

  • Issue → spec → PR: /spec pulls in the issue as live context (the line !`gh issue view $0 --json title,body,comments` in the skill body), writes the spec and links the issue; /feature finishes with gh pr create --fill --body-file docs/plans/<slug>.md; a morning routine triages new issues (labels, estimate, a draft spec for those labeled ready).
  • Prod → test → PR: Sentry/logs via CLI or MCP → a nightly routine: “new error groups in the last 24 hours → reproduce with a failing test → if reproduced, fix it and open a PR labeled from-prod; if not — an issue with hypotheses”. This is “self-healing” with a human on merge; only worth running once the gate (18.3) and the CI agent (18.8) are in place.
